Password manager pCloud Pass was hit by a cyberattack, and users got login alerts even with two-factor on

pCloud confirmed on November 27 that its pCloud Pass password manager was targeted by a cyberattack. Users reported receiving emails saying an unfamiliar device had connected to their accounts, in some cases even with two-factor authentication turned on. pCloud says the attack was promptly contained, a small number of pCloud Pass user email addresses were exposed, and login attempts were made against those accounts, with an automatic notification sent to each exposed address. pCloud says passwords, notes, and other information stored in pCloud Pass were not compromised because they are encrypted on users' devices and can only be unlocked with the master password, which pCloud does not hold. It has not said whether encrypted vaults were copied, how the attackers got in, or how many users were affected. pCloud says its cloud storage service was not affected. This is the third password manager incident this month, after mSeven's mSecure in early November and the 1Password breach disclosed November 25.

Why it matters: a lot of small businesses keep every work login in a password manager, so three password manager incidents in one month is a pattern, not a coincidence. If you use pCloud Pass, change your master password, review connected devices in Settings, turn on two-factor authentication if it is off, and watch for phishing emails that try to trick you into entering your master password or recovery words.

Sources: BleepingComputer · The Hacker News

Attackers broke into domain registrar easyDNS and took customer data and email password hashes

Domain registrar and DNS host easyDNS disclosed on November 27 that an attacker logged into its Amazon Web Services account without authorization on November 26 and took customer data. The attacker also misused some customers' own AWS keys stored for easyDNS's easyRoute53 integration, which copies DNS zones to Amazon Route 53. The stolen data can include names, email and postal addresses, and phone numbers, plus limited billing details such as the last four digits of a card and its expiry date for customers on recurring billing. For easyMail users, the attacker also took mailbox password hashes stored as unsalted SHA-256, which makes weak passwords easier to crack offline. easyDNS says no full card numbers were taken, control panel passwords and API keys were not exposed, and domains, DNS, email and web forwarding kept working. The easyRoute53 integration is offline while the investigation continues.

Why it matters: small businesses register their domain, run their DNS, and host business email through registrars like easyDNS, so a breach there puts the shop's domain and email at risk. If you use easyDNS, change your easyMail password now and change it anywhere else you reused it, and if you stored your own AWS keys in easyDNS for Route 53, deactivate and delete that key in AWS and create a fresh one.

Sources: easyDNS data breach notice · Privacy Affairs

A 12-year-old flaw in Linux file sharing hands attackers root with one network connection

Researchers at OpenSec disclosed on November 25 a flaw in the Linux kernel's built-in NFS file server, tracked as CVE-2026-99362 and nicknamed NFS2ROOT, that lets an unauthenticated attacker get a root shell on a vulnerable server with a single TCP connection to port 2049, no login and no file mount needed. The bug has been in the kernel since 2014. It sits in the reply cache for NFS version 4.1 and 4.2 sessions: a client can negotiate the cache down to zero bytes, then trick the server into copying a full reply into it, writing past the end of a kernel memory object. OpenSec chained that into a working root shell and published a video of the attack. The Linux kernel team scores the flaw 9.8 out of 10. Fixes are in kernel 6.12.117, 6.18.61, 7.3.2 and 7.4-rc1, with backports to older supported kernels, though some distributions still have no fix out. There is no confirmed exploitation in the wild yet, and OpenSec has kept its exploit code private, but the flaw needs only a reachable NFS server.

Why it matters: small businesses run Linux file servers and NAS boxes that share files over NFS, and this flaw turns a reachable file server into a full system takeover with no password. Check whether your file server or NAS runs the kernel NFS server on an exposed port 2049, install the patched kernel your vendor ships, and do not expose NFS to the internet.

Sources: BleepingComputer · OpenSec advisory

AI agents have now broken into real companies, including small ones, and Switzerland just confirmed it

Switzerland's National Cyber Security Centre confirmed this week that attackers using AI agents have broken into computer systems at Swiss organizations in four of five confirmed cases, the first such cases in the country. Three of the attacks targeted critical infrastructure operators, and two of those succeeded. Small and medium-sized companies were among the organizations hit, and they came forward voluntarily. The agency calls the tools agentic offensive frameworks: AI agents that find security weaknesses and carry out attacks on their own, scanning for known unpatched flaws, running many attacks in parallel, and switching methods when defenses respond. Britain's National Cyber Security Centre reported the same pattern this week, with a marked rise in AI-assisted attacks since September 2026, and Italy's incident response team described AI-directed agents breaking into a large number of systems within a few hours. The weaknesses the agents exploited are old ones: credentials committed to code repositories, misconfigured infrastructure, default or missing authentication, and weak APIs. What has changed is speed, persistence, and cost.

Why it matters: this is the first official confirmation that AI agents are breaking into small businesses, not just big targets, and they do it by chaining the same basic weaknesses a routine security check would catch. Patch internet-facing systems fast, require MFA or passkeys on everything reachable from the internet, remove credentials from code and repositories, and take internet-facing systems that cannot be patched quickly offline or behind authentication.

Hackers broke into Todoist and stole password hashes for about 6 percent of users

On November 24, task management app Todoist said an attacker got into its production systems on November 22 and 23 and downloaded account records for about 6 percent of its users. The attacker used a stolen credential for Todoist's version control system to change automated workflows in three code repositories, then obtained more credentials, took over an employee's work account, and reached the company's cloud infrastructure. The downloaded records hold email addresses, account creation dates, and password hashes for early users whose passwords were stored with an older method, salted SHA-1. The attacker also took Todoist API tokens and Slack integration tokens for about 0.003 percent of users, searched some users' tasks and comments for credentials, and pulled email details through the Todoist for Outlook add-in for about 0.001 percent. Todoist says it found no changes to its application code and no sign the attacker signed in to accounts in the main affected group. It blocked the attack path, rotated exposed credentials, reset affected passwords, retired the old hashing method, and disabled the Outlook add-in.

Why it matters: Todoist is the to-do list a lot of small teams run their work on, and the stolen hashes belong to early accounts, which often means the business owner who set the account up years ago. If your shop uses Todoist and got a notice, reset the password and change it anywhere else you reused it. If anyone on the team stored passwords or API keys inside a Todoist task, revoke and replace those credentials now.

Hackers slipped a remote control trojan into official downloads of two popular Windows utilities

Researchers at AhnLab's Security Intelligence Center found that installers for Q-Dir and DesktopOK distributed from the official SoftwareOK website had been tampered with. The confirmed poisoned versions are Q-Dir 12.83.0.0, 12.84.0.0 and 12.85.0.0, and DesktopOK 12.82.0.0 and 12.85.0.0. The malicious files arrived both in direct downloads and through the update process of already installed legitimate programs. The installer runs the genuine program so nothing looks wrong, while in the background it downloads a Python-based remote access trojan from an external server, using a legitimate 7-Zip tool to unpack it. Once installed, the trojan can run shell commands and Python code, transfer files, capture screenshots and collect system details, and it sets up persistence with a scheduled task that impersonates Microsoft Edge. AhnLab has not determined how the installers were replaced, and cautions that the confirmed versions may not cover everyone exposed while the tampered files were being served.

Why it matters: Q-Dir and DesktopOK are free Windows utilities found on a lot of small business PCs, and this attack came through the official download page, not a shady mirror. If anyone on your team downloaded or updated either program recently, uninstall it, reinstall the latest release, and check the installer SHA-256 hash against the one posted on the download page. Also look for the scheduled task impersonating Microsoft Edge and for unexpected files under ProgramData, and treat any machine that ran a tampered installer as compromised until it has been checked.

North Korea-linked hackers hid malware in 7,600 GitHub projects, and opening one in VS Code can run it

Researchers say a North Korea-linked campaign called PolinRider has planted a small Python loader in more than 7,600 GitHub repositories owned by about 2,330 accounts, most of them developers. The loader hides in ordinary project files such as a small utils package or conftest.py, and in some cases in a hidden VS Code task, so simply opening the project folder in VS Code can be enough to trigger it. When it runs, it fetches JavaScript stored in an Ethereum transaction, which points it to the attacker's server and delivers a second stage. That stage scans the machine for developer tools such as GitHub Desktop, Cursor and VS Code, tampers with the most used ones, and steals credentials. The loader was pushed to about 2,040 repositories between October 27 and November 6. The same loader was also force-pushed into open pull requests at AsyncAPI Generator, CircuitVerse, Open Food Facts and Jaeger in October, and CircuitVerse's release workflow actually ran it. SafeDep found the loader in 375 public repositories on November 24, and Apiiro counts at least 7,609 affected repositories in total.

Why it matters: small dev teams and shops that build on open source software pull code from GitHub every day, and this campaign turns a routine clone, or a project folder opened in VS Code, into an infection. Do not run or import a project you did not expect to change, check your own repositories for unexpected commits and new files, and rotate any credentials that were on a machine that ran a suspicious project.

Sources: The Hacker News · StepSecurity

1Password breach exposed customer names and emails, but vaults were not touched

On November 25, password manager 1Password disclosed that an attacker broke into some of its backend systems and copied account records for a subset of customers. The attacker got in through an employee's corporate GitHub account, which 1Password began investigating on November 19. From there the attacker reached private source code, pushed malicious code into backend services, and downloaded customer records: names, sign-in email addresses, account and user identifiers, account creation and last sign-in times, public keys, Secure Remote Password parameters, and tokens from some invitation, provisioning and account recovery email links. The attacker also copied private source code and got into 1Password's CI/CD system, which holds infrastructure secrets. 1Password says customer vaults, the items in them, the keys that protect them, and account recovery keys were never accessed or available to the attacker, and it does not store account passwords or Secret Keys. It has disabled the compromised GitHub account, revoked the stolen token, rotated internal credentials, and lengthened the codes in invitation and recovery emails from six digits to ten alphanumeric characters. It says it found no evidence of account takeovers using the exposed tokens, and users with outstanding invitations or recovery links were notified individually.

Why it matters: a lot of small businesses keep every work password in 1Password, so a breach at the password manager itself gets attention fast. The good news is the vaults were not reached, and 1Password says no action is needed in your account. The real risk is phishing: the stolen names and sign-in emails are exactly what a convincing fake 1Password email needs. Never enter your account password or Secret Key from an email link, and use the official app or website instead.

Hackers are exploiting a critical Drupal flaw to take over websites

Drupal's security team has confirmed that attackers are exploiting a critical flaw in Drupal core on live sites, with attacks reported as early as November 19. The flaw, CVE-2026-132165, sits in the installer file that ships with Drupal core. Under certain conditions, an anonymous attacker can use the installer to try to reinstall an existing site, which can lead to a full site takeover or remote code execution, with no login needed. Drupal rated the flaw highly critical, 20 out of 25, and released fixes on November 18 in Drupal 10.6.22, 11.3.22 and 11.4.13. On November 24, CISA added the flaw to its Known Exploited Vulnerabilities catalog and gave federal agencies until November 27 to fix it. Sites on Drupal 11.2 and older, or 10.5 and older, get no fix at all, and about 29 percent of sites reporting usage data were running those end-of-life branches.

Update, November 25: Drupal has disclosed a second flaw, CVE-2026-136716, rated highly critical at 21 out of 25. The November 18 fix did not protect sites in unusual or incomplete install states, and those sites can still be taken over through the installer, including production sites. Drupal says this flaw is also being exploited in the wild, and any site that left its installer remotely accessible after the first fix may already be compromised, even though the vulnerable state does not show in the admin interface. The fix is in Drupal 10.6.23, 11.3.23 and 11.4.14, and after updating, sites must run update.php to complete the repair. Sites that already blocked /core/install.php are not affected.

Why it matters: Drupal powers a lot of small business, nonprofit and community websites, often set up years ago by a contractor who has since moved on. If your site runs Drupal, ask your web provider which version it is on and update to 10.6.22, 11.3.22 or 11.4.13 right away. If you cannot update today, block access to /core/install.php in the web server configuration or the .htaccess file, and if your site is on an end-of-life branch, plan the upgrade now because no patch is coming for it.

Sources: BleepingComputer · Drupal security advisory · The Hacker News (CVE-2026-136716)

Attackers ran code on six servers of the Hex.pm package registry

On November 23, an attacker exploited a critical flaw in Hex.pm, the package registry Elixir and Erlang developers use to fetch dependencies, and ran operating system commands on six of its production web servers. The flaw, CVE-2026-129514, scores a maximum 10.0 and needs no login. It sat in the code that reads request bodies since February 2016. Hex.pm's team blocked the attack and had every server on a patched build within about 15 minutes of the first malicious request, and found no evidence that packages were changed. But the team cannot rule out that the attacker read account data, because database reads are not logged. Email addresses, password hashes, API key hashes, two-factor secrets, sessions and audit logs may have been seen. Hex.pm rotated its credentials and signing keys, which logged everyone out, and told users to change passwords and reset two-factor authentication. Self-hosted copies of the registry software are affected until they deploy the patch.

Why it matters: small dev shops that build with Elixir or Erlang pull their dependencies from Hex.pm, and a compromised registry is how poisoned packages reach a build. If your team uses Hex.pm, change the account password, reset two-factor authentication, rotate API keys, and fetch packages only from repo.hex.pm until Hex ships clients with its new signing system.

Radware breach exposed some customers' cloud access keys

Cybersecurity company Radware says attackers reached an internal Cloud WAF management API that was left exposed to the internet without authentication, and may have accessed customer contact details and the credentials some customers configured to export logs to their own cloud storage. The unauthorized access happened on November 19, and Radware detected it about ten hours later, blocked the source and revoked and replaced its internal credentials. The credentials at risk are AWS S3 access keys, Azure Blob Storage keys or shared access signatures, and SFTP logins used for log export. Radware says it found no evidence that attackers changed customer security policies or reached application traffic, certificates or end-user data, and it is still investigating whether the exposed credentials were used. It has already received reports from customers about AWS alerts for an unfamiliar IP address trying to access their log-export buckets. Radware has not said how many customers were affected, and it has not yet issued a public statement or filed a breach report with the US Securities and Exchange Commission.

Why it matters: small businesses that use a cloud web application firewall often send their logs to their own AWS or Azure storage, and the keys for that storage were the thing exposed here. If your shop uses Radware Cloud WAF, rotate the log-export credentials right away and review your cloud storage access logs back to November 19 for activity from unfamiliar addresses.

Two billion stolen passwords and session tokens sat in an open database anyone could read

Security researcher Jeremiah Fowler found a publicly accessible database holding about two billion login credentials, with no password and no encryption on it. The records include email addresses, usernames, passwords, cookies, session tokens and device details, gathered into 8,471 folders. Fowler says the data looks like it came from infostealer malware, which steals every login saved on an infected computer, and about 400,000 documents profile individual victims in detail, enough to take over their digital lives. The most common accounts in the trove are Gmail, with 608 million records, and other Google services. No single company was breached to build the collection. Fowler reported it to the hosting company, which has since restricted access, but nobody knows how many people read it first.

Why it matters: small business owners and staff reuse passwords across work and personal accounts, and session tokens in a leak like this can let an attacker straight into an account without a password at all. Run a malware scan on any computer that feels off, then change passwords from a clean device, starting with email and banking, and turn on MFA everywhere it is offered. A password manager makes the rotation far less painful.

Attackers exploited a Microsoft Azure flaw to steal customers' API credentials

Microsoft is warning customers that attackers exploited a flaw in Azure API Management, the service that publishes and guards APIs, and used it to steal credentials stored in customer instances. The flaw affected the Classic tiers (Developer, Basic, Standard and Premium) that were not configured to Microsoft's recommended security settings. Attackers could reach secrets stored as Named Values, client secrets for identity and OpenID Connect providers, subscription keys and tokens used to call management APIs. Microsoft found the flaw on November 18 and closed the access path on November 19, and says the newer APIM v2 tiers were not affected. Norway's National Security Authority linked the flaw to attacks on energy companies Equinor and Skagerak Energi, and says organizations in other countries and sectors were hit too. Microsoft's fix stops further access, but it does not invalidate credentials that were already stolen.

Why it matters: small dev shops and businesses that run APIs on Azure often store keys and secrets in API Management, and a stolen key can open the backend systems behind the API. If your shop uses Azure API Management Classic, rotate every secret stored in it, plus the downstream credentials those secrets unlock, and check logs for unusual management activity since mid-November.

Hackers planted a backdoor in six WordPress plugins, but the poisoned updates never reached a site

Attackers used a compromised WordPress.org account belonging to plugin maker WP connect to push backdoored releases of six WordPress plugins on November 22, including Air WP Sync, WP Sync for Notion, add-ons for Contact Form 7 and Gravity Forms, and an Airtable sync for WooCommerce. The releases added a file that phones home to an attacker server and runs whatever PHP code the server sends back, with no login needed. It can run shell commands, read and change files, dump the site's user table including password hashes, and plant webshells. Wordfence, which found the backdoor, rates it CVE-2026-135202 at CVSS 9.8. The good news is that WordPress.org's release safeguards flagged and blocked the malicious versions before they were distributed, so no site received them through updates, and no exploitation of live sites has been reported. All six plugins were closed on WordPress.org the same evening, and there is no patched version, since the code was added on purpose rather than by mistake.

Why it matters: small business WordPress sites use these sync plugins to connect forms and shops to Airtable and Notion, and the six plugins together have more than 3,600 active installations. If your site runs any WP connect plugin, check for the file includes/airwp-online.php and for outbound traffic to tascredit-pay.com, then remove the plugin and run a full malware scan.

A critical flaw in a long-dead ASP.NET library is being exploited, and there will never be a patch

Mandiant disclosed on November 18 that a legacy ASP.NET anti-CSRF library called Idunno.AntiCsrf has a critical deserialization flaw, CVE-2026-131914, scored CVSS 9.3. A remote attacker can run code on the web server with a single unauthenticated web request, no login needed, and Mandiant says active exploitation in the wild has been observed. The library was last released in December 2008 and the project is defunct, so no fix exists and none is coming. The only remediation is to remove the library from every application that loads it and replace it with a supported anti-CSRF mechanism.

Update, November 24: CISA has added CVE-2026-131914 to its Known Exploited Vulnerabilities catalog, with a federal remediation deadline of November 27. Mandiant also advises rotating machineKey and other Web.config secrets if exploitation is suspected.

Why it matters: small businesses running older ASP.NET websites may still load this library without knowing it, since it sits quietly in the site's configuration. If your site runs on ASP.NET WebForms, check its Web.config files and application folders for Idunno.AntiCsrf and remove it. An unpatched flaw that can never be patched, and that attackers are already using, is exactly the kind of thing a routine scan will find.

Sources: The Hacker News · Mandiant advisory

Hackers used GL.iNet's cloud service to plant malware on routers and remote-control KVM devices

GL.iNet confirmed on November 20 that hackers exploited a flaw in its GoodCloud cloud remote management service to install custom malware on some customers' routers and KVM devices. GoodCloud lets owners manage routers remotely and control computers plugged into GL.iNet KVM devices, so an infected KVM can reach the computer attached to it. The malware includes root-level reverse shells that call back to attacker servers, plus a script that disguises itself as a system process, installs SSH keys for remote access, and survives reboots. GL.iNet says it fixed the cloud flaw and blocked the attack path on November 20, so no new devices can be infected that way, but the fix does not clean devices that are already infected. Owners must install the new security firmware for their exact model, even if the device looks clean, and check any computer attached to an infected KVM. GL.iNet has not said how many devices were hit or how the attackers got into its cloud service.

Why it matters: GL.iNet travel routers are popular with remote workers and small shops that need a portable office network, and its KVM devices sit between an admin and the computers they manage. If your shop runs a GL.iNet router with GoodCloud turned on, or a GL.iNet KVM, install the security firmware now and check the device for a process disguised as crond -i /tmp/.log.

Hackers stole credit card numbers and CVVs from software checkout provider Cleverbridge

E-commerce platform Cleverbridge warned on November 22 that hackers breached its systems and copied customers' payment card data, including card numbers, expiration dates and CVV security codes. Cleverbridge handles checkout, payments and subscriptions for software and SaaS companies, including brands like Red Hat, SUSE, Tenable, Veeam, Jamf and Parallels. It detected unauthorized activity on November 4 and took systems offline the same day, then began notifying affected customers on November 20. It has not said how the attackers got in, how long they were inside or how many customers were affected. It says the incident was not ransomware, no other personal data such as names or billing details was copied, and it is working with TransUnion's Cyberscout on credit monitoring and fraud assistance for affected customers.

Why it matters: small businesses buy a lot of their software through checkout providers like Cleverbridge, often without ever seeing the name. If you bought software online and a card you use for business purchases was charged through Cleverbridge, watch the statement for unauthorized charges and ask your card issuer about a replacement card.

AI providers were quietly copying customer prompts for months, and OpenRouter just cut three of them off

Security researchers at Dragos spent five months, July through November, sending about two million AI prompts laced with unique canary links and credentials to widely used AI services, then watching where those secrets surfaced. They found attackers actively stealing data from inside three AI inference providers, none of which knew it had been breached until the researchers told it. The planted prompts were processed alongside real customer requests, which were almost certainly copied too. On November 22, OpenRouter, the gateway that routes customer AI requests to third-party providers, said it removed three providers from its platform, stripped 125 endpoints of their Zero Data Retention status and notified affected customers. OpenRouter says it was not itself breached. One provider, Phala, said an attacker took control of an inference server and that requests sent to one DeepSeek model through it between October 21 and November 8 should be treated as exposed.

Why it matters: small businesses and dev shops send AI prompts that often contain real secrets, customer data and internal details, and many picked providers that promised not to keep the data. If your shop uses AI tools through OpenRouter or a cheap inference provider, treat anything you sent as possibly read by a third party and rotate any secret that appeared in a prompt.

Rackspace cloud breach let hackers read customer Kubernetes secrets

Rackspace warned customers on November 21 that hackers breached its Rackspace Spot cloud platform on November 17 using leaked credentials. The attackers acted as legitimate users in some customer organizations, created unauthorized pods in Kubernetes clusters, read Kubernetes Secrets and listed nodes and volumes. Kubernetes Secrets can hold passwords, tokens and API keys for databases and cloud services. Rackspace says it revoked affected tokens and sessions, removed the unauthorized pods and rotated keys, and told affected customers to reissue API tokens, replace refresh tokens and rotate every credential stored in their cluster Secrets. Service was fully restored on November 21 after an extended outage of the admin console.

Update, November 24: Rackspace has decided to shut down the Spot platform entirely. The service will be permanently discontinued on December 8, 2026, and Rackspace is telling all Spot customers to move their workloads and download their data before then. Rackspace now says every Spot customer should treat API tokens, refresh tokens, kubeconfigs and Kubernetes Secrets as potentially compromised, whether or not they received a breach notice, and review access logs back to November 16.

Why it matters: small dev shops and businesses that run containerized apps on a cloud platform trust the provider to guard their secrets. If your shop runs anything on Rackspace Spot, rotate the credentials the breach could have reached and check logs back to November 17.

Microsoft says attackers exploited a flaw in Entra Connect Health and stole tenant data

Microsoft told administrators on Friday, November 21, that attackers exploited a flaw in its Entra Connect Health service and got read-only access to tenant data. The exposed information included email addresses of tenant technical contacts and administrator accounts, plus tenant IDs, display names, domain names, license tiers and sync status. Microsoft says no passwords, password hashes, authentication tokens or valid cryptographic keys were exposed. It found the flaw on November 9, deployed a server-side fix on November 19, finished its investigation on November 20 and began notifying affected organizations. Microsoft has not said how many tenants were hit or when the attacks began.

Hijacked GitHub accounts are scanning the web for unpatched Next.js sites and posting the stolen keys in public

Researchers at OpenSourceMalware reported on November 18 on a campaign they call React2STEAL. Attackers are using 45 hijacked GitHub accounts to run automated scans from GitHub's own servers, looking for Next.js websites still open to React2Shell, a critical flaw scored 10.0, and a related Next.js bypass. When a scan finds a vulnerable site, it steals environment files, cloud credentials and AI provider keys, then commits the loot to a public GitHub repository where anyone can read it. Researchers found at least 1,281 victim hostnames across about 1,100 domains, and about 7.4 gigabytes of stolen data sitting in public repos. The campaign was still adding new results every 11 minutes when the research was published. The hijacked accounts overlap with the wfx credential-stealing campaign reported here on November 13.

Why it matters: small dev shops and small businesses that run a Next.js site or build with GitHub Actions are the target here, and the stolen data includes Stripe keys and cloud credentials that can drain money or take over infrastructure. If your shop runs Next.js, make sure it is patched against React2Shell, and if a server was ever unpatched, rotate every secret that server could reach.

Seven critical PHP flaws can let attackers run code on web servers, and older PHP gets no fix

On Thursday, November 19, the PHP project released fixes for 18 flaws, seven of them rated critical at CVSS 9.2. The worst, CVE-2026-129289, is a request smuggling flaw in PHP-FPM: an unauthenticated attacker can slip a second request into a reused backend connection and run their own PHP code on the server, with no login and no special setup. The other critical flaws sit in session handling and the PHP engine, and several can also lead to code execution. The fixes are in PHP 8.2.36, 8.3.37, 8.4.28, 8.5.13 and 8.6.0. None of the flaws is in CISA's actively exploited list, and no attacks in the wild have been reported.

The catch is that PHP 8.1 and older get no fix at all, and three of the new flaws trace back to gaps in the October PHP2Shell fixes. The November fix also turns session upload progress off by default, so sites that rely on it need to turn it back on after updating.

Why it matters: a huge share of small business websites run on PHP, usually through WordPress on shared hosting, and the shop rarely controls the PHP version itself. If your site runs on PHP, ask your web host whether it has updated to a fixed build, and whether your site is still on PHP 8.1 or older, which will never get this fix.

Critical NGINX flaws (NGINX2Root) can hand attackers control of web servers, and a proof of concept is already public

On November 18, F5 released out-of-band fixes for five critical remote code execution flaws in NGINX. Researchers call the set NGINX2Root, and F5 rates all five at CVSS v4 9.2. The headline flaw, CVE-2026-123007, is a memory corruption flaw in HTTP/2 flow control. It needs no login, has been present since NGINX 1.9.5 in 2015, and Rapid7 has published a public proof of concept. The other four are use-after-free flaws: CVE-2026-123633 in HTTP/2, CVE-2026-123634 in the DNS resolver, CVE-2026-121810 in HTTP/3, and CVE-2026-113425 in the mail proxy.

The fixes are in NGINX Open Source 1.30.7 (stable) and 1.31.9 (mainline), and in NGINX Plus builds 37.3.0.1 and 37.0.8.1. As of November 19, there is no confirmed exploitation in the wild, and none of the five flaws is in CISA's Known Exploited Vulnerabilities catalog.

Update, November 28: Singapore's Cyber Security Agency said on November 26 that CVE-2026-123007 is reportedly being actively exploited, and a proof of concept is public. F5, in its advisory updated November 27, says it has not identified reliable technical evidence confirming successful exploitation, and CISA had not listed the flaw as exploited as of November 27. The version to install is now 1.30.8 (stable) or 1.31.10 (mainline), released November 23, because 1.30.7 and 1.31.9 are still exposed to CVE-2026-132779, a medium-severity flaw that can pin a CPU core at 100 percent when TLS 1.3 early data is on.

Why it matters: NGINX sits in front of a huge share of small business websites and apps, about 225 million sites in all, and the main flaw needs only HTTP/2 enabled and no login. If your website, web app, or hosting provider runs NGINX, ask whether it has been updated to a fixed build.

Critical Java flaw (Java4Shell) can hand attackers control of servers, and Java hides inside other products

On November 17, CISA urged organizations to patch a critical flaw in Java right away. The flaw, CVE-2026-114938, nicknamed Java4Shell, sits in the fast Base64 decoder inside the Java virtual machine. Specially crafted input can crash the JVM and let an attacker run code without any login. Researchers have already shown it working against Jira, Jenkins, Confluence and Keycloak, tools small shops and MSPs run every day.

It affects Java 17 (from version 17.0.6 on), 21, 25 and 27, but only on servers with newer chips: Intel Xeon from Ice Lake on, and AMD Zen 4 and later. Standard Java 8 and 11 are not affected, and neither are ARM servers. The out-of-support lines (18 to 20, 22 to 24, 26) carry the same flaw and get no fix. Oracle and OpenJDK shipped fixes on November 17 (builds 17.0.21.1, 21.0.13.1, 25.0.5.1 and 27.0.1.1), and other Java builds, including Amazon Corretto, Azul Zulu and Eclipse Temurin, are shipping theirs on their own schedules. No attacks in the wild have been reported so far, and the flaw is not on CISA's actively exploited list.

Why it matters: Java hides inside other products, appliances and containers, and bundled copies often never show up in a software inventory, so a shop can be exposed without knowing Java is even there. Check anything that might run Java, update to your vendor's fixed build, and if you cannot patch yet, starting the JVM with the -XX:UseAVX=2 flag turns off the vulnerable fast path.
